# Approach plans and the browser

Two features asked for on 2026-11-16: an approach plan for every enriched company, and Playwright integration for reading JavaScript pages and pre-filling job applications. Research digests behind this plan: outreach cadence and UAE rules, Agent SDK custom tools, ATS forms and Playwright.

## Decisions

- **Biz enrichment is one run of three phases**: dossier, approach plan, letters (user, 2026-11-16). A failed plan leaves letters on the default routing and a missing sender name skips the letters, each with a concern. Re-plan and Write letters rerun one phase. The plan names the first contact, backups and a multi-touch sequence with day offsets, per touch: person or company inbox, channel (email, LinkedIn, phone), address, angle, hook, ask and talking points.
- **Message research applied** (user, 2026-11-16; `docs/research/2026-11-16-outreach-messages.md`): email bodies 60-100 words; the first touch is always email or LinkedIn, calls only later and flagged for TDRA approval on UAE numbers, no WhatsApp in cold plans; letters to GCC companies end with an opt-out line Python adds after naturalizing. The copywriter and planner prompts carry the research's phrasing rules.
- **Python validates the plan** (no invented contacts, routes or hooks; touch caps, gaps, guessed-email rule, email or LinkedIn first, one person a day, at most three people). Bad touches are dropped with a concern, never silently repaired.
- **Letters follow the plan**: one draft per person's opening email or LinkedIn touch, with the planned angle, hook and ask. Since 2026-11-16 every email and LinkedIn touch gets its own draft (`2026-11-16-approach-sequence.md`). Without a plan, letters keep the old routing.
- **Own browser tools, not Playwright MCP.** An in-process SDK MCP server per agent session, bound to its own browser context. The toolset has no submit, script or download verbs; a route guard allows only GET to public hosts (no localhost or private networks), and every tool call goes through that guard, so no separate PreToolUse hook. Tools are pluggable toolkits that a prompt names in `toolkits:`; an unavailable toolkit (no Chrome) leaves the agent on WebFetch with a note.
- **Form filling is pluggable per ATS** (Greenhouse, Lever, Ashby, a generic fallback; Workday opens for manual work only). One DOM scan finds fields and labels; Python never fills protected questions (EEO and demographics, salary, visa and work authorization, attestations, consent, signatures). An agent answers the remaining custom questions from the CV. A safe actor fills inputs and has no click or key verbs. While it fills, submission is switched off inside the form's frame (pages submit from change handlers, and that navigation can start after a network guard is gone) and a route aborts non-GET navigations; both are removed before the applicant takes over. Custom dropdowns (`role=combobox`) are left to the applicant, since picking one needs keys or clicks. The ATS is found from the page or its embedded frames. The run then waits at a gate while the user reviews in the visible window and clicks Submit; a confirmation page or the user's answer marks the lead sent.
- **Browser**: Playwright for Python driving the installed Google Chrome (`channel="chrome"`), so no browser download. Headless contexts for agents, one headed persistent profile at `$MOZG_OUTREACH_HOME/browser-profile` for applications.

## Milestones

1. **Approach planner core**: models, options builder from the dossier, validator, prompt, planner. → verify: recorded-output tests for each validator rule.
1. **Approach wiring**: plan inside `biz.enrich`, `biz.approach` re-plan flow and API, letters follow the plan, Approach card in ItemView. → verify: pipeline and API tests, UI build.
1. **Browser core**: `playwright` dependency, `browser/` package (service owning Playwright, guarded contexts, capped snapshots), lifespan wiring. → verify: headless tests against a local HTTP server, guard blocks POST and private hosts.
1. **Agent browser toolkit**: toolkit registry, runner mounts per-session MCP servers and hooks, prompt parsing accepts toolkit names, scout uses it. → verify: runner option tests, tool handler tests against local pages.
1. **Form filling core**: field scan, protected-field policy, ATS adapters, safe actor, answerer agent. → verify: headless tests on fixture pages modeled on each ATS; a submit attempt raises.
1. **Apply flow**: applicant profile in the seeker brief (kept out of agent payloads and the strategy hash), `seeker.apply` item flow with a browser-review gate, confirmation detection, interaction logged, UI button and gate. → verify: flow tests with a fake browser, UI build.
